CAN 버스에 흐르는 프레임 하나는 생각보다 단순합니다. **ID 하나와 바이트 몇 개**가 전부입니다.

```
ID 0xB4   데이터 00 00 00 00 1D 0B 7A 5E
```

이것만 보고는 무엇을 뜻하는지 알 수 없습니다. 그래서 「ID 0xB4는 SPEED라는 메시지이고, 그 안의 5~6번 바이트가 차속이며, 0.01을 곱하면 km/h가 된다」 같은 약속을 적어 둔 **사전**이 필요합니다. 그 사전의 표준 텍스트 형식이 **DBC**입니다. 메모장으로 열 수 있는 평범한 텍스트 파일입니다.

## 위에서 아래로: DBC의 계층

| 줄 머리 | 이름 | 담는 내용 |
|---|---|---|
| `BU_` | 노드 | 버스에 붙은 ECU 목록 |
| `BO_` | 메시지 | ID, 이름, 바이트 수(DLC), 보내는 노드 |
| `SG_` | 신호 | 메시지 안의 위치(시작 비트·길이), 바이트 순서, 부호, factor·offset, 범위, 단위, 받는 노드 |
| `VAL_` | 값 정의 | 숫자에 붙은 이름 (예: 0 = P, 1 = R) |
| `CM_` | 설명 | 메시지·신호에 붙는 주석 |
| `BA_` | 속성 | 송신 주기 같은 추가 정보 |

메시지가 신호를 품고, 신호가 값 정의를 품는 구조입니다. 실제 파일에서는 이렇게 보입니다.

```
BO_ 180 SPEED: 8 XXX
 SG_ ENCODER : 39|8@0+ (1,0) [0|255] "" XXX
 SG_ SPEED : 47|16@0+ (0.01,0) [0|250] "km/h" XXX
 SG_ CHECKSUM : 63|8@0+ (1,0) [0|255] "" XXX
```

- 첫 줄: ID 180(= `0xB4`)인 메시지의 이름은 `SPEED`, 길이는 8바이트, 보내는 노드는 `XXX`(정해지지 않음)입니다.
- 그 아래 `SG_` 세 줄이 이 메시지에 들어 있는 신호 세 개입니다.
- `47|16@0+ (0.01,0)` 은 「47번 비트부터 16비트, Motorola 순서, unsigned, raw × 0.01 + 0」이라는 뜻입니다. 이 조각들을 읽는 법은 다음 모듈에서 하나씩 익힙니다.

> [!IMPORTANT]
> DBC에는 **신호를 어디서, 어떻게 꺼낼지**만 적혀 있습니다. 실제 값은 로그의 바이트에 있고, 둘을 합치는 일이 디코딩입니다.

## DBC에 없는 것: 채널과 주기

**채널**, 즉 그 메시지가 어느 CAN 버스에 흐르는지는 DBC 안에 없습니다. 차량에 버스가 여러 개면 버스마다 DBC를 따로 두고(opendbc의 `_pt` 는 파워트레인 버스용), 측정 장비에서 「1번 채널 ↔ 이 DBC」로 연결합니다.

**송신 주기**는 `BA_ "GenMsgCycleTime"` 속성으로 적을 수 있지만, 이 repo에서 쓰는 opendbc DBC에는 없습니다. 그래서 DBC 탐색기는 실제 로그에서 관측한 버스 번호와 프레임 간격을 함께 보여 줍니다.
